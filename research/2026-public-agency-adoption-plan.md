# KRDS 연계 공공기관 적용 계획

> 작성일: 2026-08-12  
> 목적: 이 저장소의 UX Writing 도구를 실제 공공기관 디지털서비스 개선 사업에 **안전하고 검증 가능하게** 적용하기 위한 실행안  
> 범위: 공식 KRDS 적용 프로세스와 이 저장소의 린터·가이드·생성기를 연결한다. 이 문서는 법률 자문이나 조달 규격의 확정본이 아니다.

## 결론

이 프로젝트는 공식 KRDS를 대체하거나 KRDS 준수를 인증하는 제품으로 내놓으면 안 된다. 가장 적합한 역할은 다음과 같다.

> **공식 KRDS의 스타일·컴포넌트·서비스 패턴을 적용하는 과정에서, 화면 문구를 수집·검토·개선·증빙하는 UX Writing 품질 게이트**

첫 실제 적용은 **기관 1곳, 핵심 여정 1개, 비식별·공개 문구만 사용하는 8~15주 파일럿**으로 권고한다. 먼저 정적 린터와 기관별 용어 사전으로 효과를 증명하고, 생성형 AI는 기관 보안·개인정보 검토와 내부망/승인된 환경이 갖춰진 뒤에만 2단계로 도입한다.

## 1. 조사 결과: 공식 KRDS가 요구하는 적용 방식

### 1.1 공식 KRDS와 이 프로젝트의 역할 구분

공식 KRDS는 디지털 정부서비스의 원칙, 스타일, 컴포넌트, 기본 패턴, 서비스 패턴과 리소스를 제공한다. 공식 GitHub의 HTML ComponentKit도 디자인 토큰·디자인 라이브러리·HTML 컴포넌트 키트를 연계하여 공공 웹·앱의 일관성을 관리하는 체계로 설명한다.

이 저장소는 그중 **문구 레이어**에 강점이 있다.

| 공식 KRDS 적용 레이어 | 이 프로젝트가 맡을 일 | 최종 책임 |
|---|---|---|
| 서비스 패턴(신청·로그인·검색 등) | 여정별 문구 인벤토리와 상태 메시지 점검 | 기관 서비스 PM·UX 담당 |
| 컴포넌트·기본 패턴 | 버튼·입력폼·오류·도움말 등의 문구 규칙과 예시 | 디자이너·개발자·콘텐츠 책임자 |
| 스타일·접근성 | 문구의 명확성·일관성 점검, 접근성 검토 자료 제공 | 접근성 담당 및 검수 주체 |
| 운영·성과점검 | 린트 결과, 개선 이력, VOC·분석 지표의 전후 비교 | 기관 운영 조직 |

따라서 린트 점수나 생성 결과만으로 **“KRDS 준수”, “KWCAG 준수”, “접근성 인증”**을 판정하면 안 된다. 도구 결과는 검토 근거이며, 각 기관의 공식 체크리스트·사용성 평가·접근성 검수와 함께 판단해야 한다.

### 1.2 공식 KRDS 정부 관계자 가이드에서 확인한 원칙

공식 KRDS의 [정부 관계자 시작하기](https://www.krds.go.kr/html/site/outline/outline_04.html)는 다음을 명시한다.

- 발주·기획 단계에서 적용 대상, 의무·권고·예외를 고려해 준수 범위를 정한다.
- RFP의 “준수 규정”과 “품질 요구사항”에 분석·설계·구현·테스트 전 단계의 가이드 적용 및 점검을 명시한다.
- 서비스 패턴은 **필수(Do) → 권장(Better) → 우수(Best)** 순으로 적용한다. 상위 수준을 적용해도 하위 수준의 준수가 자동으로 보장되지는 않는다.
- 신규 구축·개편은 분석 → 설계 → 구현 → 테스트에서, 운영 서비스는 현황 점검 → 계획 → 개선의 반복으로 적용한다.
- 자체 검증 체크리스트와 사용자 피드백·웹 분석을 활용해 적용 전후 성과를 비교한다.

이 저장소의 활용 방식도 이 흐름을 따라야 한다. 즉, 먼저 화면과 과업을 정하고, 필요한 KRDS 항목을 매핑하며, 문구 규칙을 합의한 다음, 린터·사전·사람 검토로 증빙을 남긴다.

### 1.3 공식 자료 이용 시 유의점

KRDS 저작권 정책은 KRDS가 권리를 모두 가진 디자인·코드·문서 등은 출처 표기 후 이용할 수 있다고 안내한다. 다만 제3자 권리, 상표·로고 사용, 최신 이용 조건은 개별 기관과 공식 정책을 다시 확인해야 한다.

프로젝트 외부 공개물에는 아래 문구를 사용한다.

> 본 도구는 대한민국 정부 디자인 시스템(KRDS)을 참고하여 만든 독립적인 UX Writing 보조 도구입니다. 공식 KRDS의 승인·인증·운영 주체가 아니며, 최종 준수 여부는 기관의 공식 검수 절차로 판단합니다.

### 2.3 즉시 바로잡아야 할 대외 표현

다음 표현은 공공기관 제안·계약·검수에서 신뢰 리스크가 크므로 첫 파일럿 전 수정한다.

1. `KRDS 고시에 따라 의무를 이행`처럼 법적 의무를 단정하는 표현
2. “KWCAG 텍스트 준수율 100%”, “KWCAG 언어 접근성 전항목 Pass”처럼 도구만으로 보장하는 표현
3. “나라장터 규격 준수”, 일률적인 수의계약 기준·품목 코드·대금 지급 조건처럼 기관·사업별로 달라질 수 있는 표현
4. “KRDS 공식”이라는 수식어가 프로젝트의 자체 원칙, 사례, 문구에 붙는 표현
5. 출처가 없는 수치·연구 인용 및 자체 도입 트랙을 KRDS 공식 정책처럼 보이게 하는 표현

대신 `공식 KRDS 가이드를 참조하여 기관이 정한 적용 범위에서`, `접근성 전문 검수와 병행하여`, `발주기관 조달·계약 기준에 따라`, `기관 검토 후 확정`으로 표현한다.

## 3. 권장 도입 모델

### 3.1 3단계 배포·사용 모델

| 단계 | 목적·입력 데이터 | 배포 방식 | 생성형 AI | 현재 프로젝트 적합도 | 권장 여부 |
|---|---|---|---|---|---|
| 1. 오프라인 문구 감사 | 공개 화면, 더미·비식별 문구, 정책 검토가 끝난 문구 | 담당자 PC 또는 폐쇄망의 정적 린터/CLI | 사용하지 않음 | 높음 | **첫 파일럿 권장** |
| 2. 내부 협업 도구 | 기관 승인 문구와 내부 가이드 | 기관 내부망 또는 승인된 전용 환경 | 기관 승인 모델·게이트웨이만 사용, 사람 검토 필수 | 중간 | 1단계 성과 후 도입 |
| 3. 외부 SaaS | 여러 기관의 문구를 처리 | 외부 클라우드 | 외부 모델 또는 인증된 모델 | 낮음 | 별도 보안·개인정보·조달 검토 후에만 검토 |

1단계에서 처리할 수 없는 개인정보, 민감정보, 비공개 정책자료, 인증정보, 실제 민원 내용은 입력하지 않는다. 문구가 개인을 식별하지 않더라도 보안등급·업무 기밀성은 기관의 데이터 분류 기준으로 판단한다.

### 3.2 공식 KRDS 적용 흐름에 붙이는 위치

```text
기관 과업 선정
  → KRDS 적용 범위·Do/Better/Best 확정
  → 화면·문구 인벤토리 및 기준선 측정
  → KRDS 컴포넌트/서비스 패턴 매핑
  → 기관 UX Writing Rule Pack 합의
  → 린터 + 전문가 검토 + 법정문구 검토
  → 디자인·개발 반영
  → 접근성/사용성 테스트와 자체 체크리스트 검수
  → 배포 전후 VOC·분석 지표 비교 및 운영 반영
```

이 도구는 `Rule Pack 합의`와 `린터 + 전문가 검토` 구간에서 쓰며, 디자인 시스템 자체나 최종 인증 절차를 대신하지 않는다.

### 3.3 기관별 Rule Pack의 최소 구성

| 항목 | 내용 | 승인자 |
|---|---|---|
| 적용 범위 | 서비스, 화면 ID, 핵심 여정, KRDS 관련 가이드 버전 | 서비스 PM |
| 용어 사전 | 금지어·권장어, 첫 등장 병기, 법정 용어 예외 | 업무 부서 + 법무/정책 담당 |
| 보이스·톤 | 존대 수준, 시민 호칭, 오류·완료 메시지 방식 | 콘텐츠 책임자 |
| 컴포넌트 규칙 | 버튼, 입력폼, 오류, 도움말, 빈 상태 등의 문구 기준 | UX·개발 책임자 |
| 접근성 검토 항목 | 레이블, 오류 인지, 상태 전달, 대체 텍스트 관련 검토 항목 | 접근성 담당 |
| AI 사용 경계 | 입력 허용 등급, 금지 데이터, 모델/리전, 보존·로그 정책 | 보안·개인정보 책임자 |
| 변경 이력 | 규칙 ID, 근거, 승인일, 적용 화면, 폐기일 | Rule Pack 관리자 |

바로 사용할 수 있는 작성 양식은 [기관 UX Writing Rule Pack 템플릿](./agency-rule-pack-template.md)에 두었다.

## 4. 첫 공공기관 파일럿 실행 계획 (8~15주)

### 4.1 대상 선정 원칙

첫 대상은 중앙부처 전체 서비스나 민감 민원 서비스보다 아래 조건을 충족하는 기관·서비스가 좋다.

- 하나의 명확한 핵심 여정이 있다. 예: 예약, 교육 신청, 증명서 안내, 지원사업 신청의 안내·입력 단계
- 공개 문구 또는 비식별 테스트 문구만으로 개선 효과를 검증할 수 있다.
- 콘텐츠·UX·개발·보안 담당자가 주 1회 의사결정을 할 수 있다.
- 변경 가능한 화면과 배포 창이 있고, 적용 전후 데이터 또는 사용자 피드백을 확보할 수 있다.
- 기관이 KRDS 적용·개편 사업과 연결할 의사가 있다.

제외 대상은 주민등록번호·건강정보·상담 원문·민원 원문 등 민감한 입력을 다루거나, 법정 문구 변경 승인 창구가 없는 서비스다.

### 4.2 단계별 일정과 산출물

| 단계·기간 | 핵심 활동 | 기관 제공 사항 | 수행 산출물 | 종료 게이트 |
|---|---|---|---|---|
| 0. 착수 전 (1~2주) | 적용 범위, 정보등급, 배포모델, 법정 문구 책임자를 확정 | 보안·개인정보 검토 창구, 테스트 환경 여부 | 적용 범위서, 데이터 처리 경계서, 역할·책임 분담표 | 외부 AI 사용 여부와 입력 금지 범위 서면 확정 |
| 1. 기준선 진단 (1~2주) | 화면·문구 수집, 핵심 여정 선정, 기존 VOC·분석지표 확인 | 화면 목록, 공개 URL/테스트 계정, 기존 가이드 | 화면·문구 인벤토리, 이슈 목록, 기준선 리포트 | 범위 내 화면 100% 식별, 우선순위 합의 |
| 2. 기준 설계 (2주) | 공식 KRDS 항목 매핑, 용어·톤·예외와 상태 메시지 규칙 합의 | 업무·법정 용어 검토, 브랜드 정책 | 기관 Rule Pack v0.1, KRDS 매핑표, 승인 매트릭스 | 업무·UX·법정문구 담당자 승인 |
| 3. 개선·프로토타입 (2~3주) | 린터 1차 점검, 전문가 재작성, 디자인·개발 반영안 작성 | 화면 맥락·정책 조건·개발 난이도 | Before/After 시트, Figma/개발 전달표, 이슈 수정 목록 | 고위험 이슈 해결안 및 예외사항 승인 |
| 4. 검증·반영 (1~2주) | 자체 체크리스트, 키보드·스크린리더 포함 접근성 검토, 5~8명 내외 과업 테스트 또는 대체 검증 | 테스트 참여자 또는 VOC, QA 환경 | 검증 결과, 미해결 이슈, 배포 승인안 | 필수(Do) 항목과 계약상 수용 기준 충족 |
| 5. 배포·성과평가 (2~4주) | 배포 전후 데이터·VOC 비교, 담당자 교육, 운영 절차 이관 | 분석 데이터·운영 담당자 | 성과 보고서, 운영 매뉴얼, Rule Pack v1.0 | 지속 운영/확대/중단 결정 |

### 4.3 역할·책임 분담 매트릭스

| 역할 | 책임 |
|---|---|
| 기관 사업 책임자 | 범위·예산·최종 수용 결정 |
| 서비스 PM/업무 부서 | 실제 업무 규칙, 법정·정책 문구의 정확성 승인 |
| UX·디자인 | KRDS 패턴/컴포넌트와 화면 문맥의 적합성 검토 |

### 4.4 수용 기준과 성과 지표

계약서에는 “린트 점수 향상”만 넣지 않는다. 시작 시 기준선을 측정하고, 아래 항목 중 서비스 성격에 맞는 지표를 선택해 목표값을 합의한다.

| 범주 | 권장 측정 | 판정 방식 |
|---|---|---|
| 범위 | 선정 화면·문구 인벤토리 완결성 | 화면 ID와 현행/개선 문구의 대응표 |
| KRDS 적용 | 핵심 여정의 Do 항목 충족 여부 | 공식 가이드 링크와 자체 체크리스트 |
| 문구 품질 | 심각도 높은 행정어·모호한 CTA·오류 복구 문구 해결률 | 린트 결과 + 사람 검토 이력 |
| 사용성 | 대표 과업 완료율, 완료 시간, 이해도/신뢰도 | 적용 전후 동일 과업 테스트 또는 VOC |
| 접근성 | 계약 범위의 레이블·오류·상태 전달·키보드/보조기기 검토 결과 | 접근성 담당의 별도 검수 |
| 운영성 | Rule Pack 변경 요청 처리 시간, 재사용률, 교육 후 자체 검토 가능 여부 | 운영 대장과 담당자 설문 |

## 5. RFP·제안서에 넣을 요구사항

### 5.1 안전한 요구사항 문구 예시

```text
수행사는 발주기관이 정한 KRDS 적용 범위 및 최신 공식 가이드를 참조하여
핵심 사용자 여정의 UI/UX와 UX Writing 개선안을 제시한다.

수행사는 분석·설계·구현·테스트 단계별로 KRDS 관련 적용 항목과
문구 품질 기준을 추적할 수 있는 매핑표 및 검수 이력을 제출한다.

자동화 도구의 점검 결과는 보조 근거로 활용하며, 법정 문구의 정확성,
접근성 적합성 및 최종 KRDS 적용 여부는 발주기관의 승인·검수 절차로 확정한다.

개인정보·민감정보·비공개 업무정보의 외부 생성형 AI 입력은 금지한다.
생성형 AI를 사용하는 경우, 모델·처리 위치·보존·로그·접근권한·삭제 절차를
발주기관 보안 및 개인정보 담당자의 사전 승인 대상으로 한다.
```

### 5.2 최소 산출물

1. 적용 범위·데이터 처리 경계서
2. 화면·문구 인벤토리 및 KRDS 매핑표
3. 기관 UX Writing Rule Pack(용어 사전, 예외, 톤, 컴포넌트별 규칙)
4. Before/After 개선 시트와 법정 문구 검토 이력
5. 자체 체크리스트 및 접근성·사용성 검증 결과
6. 배포 전후 성과 보고서와 운영·교육 자료

### 5.3 기존 B2G 문서의 사용 원칙

`b2g-service-package/`의 제안서·SOW·가격 문서는 **초안 골격**으로만 사용한다. 사업 발주 전 다음을 기관 계약·조달 담당자와 최신 기준으로 확정한다.

- 계약 방식, 입찰·평가 기준, 단가, 대금 지급 조건, 하자보수 조건
- SW사업/컨설팅/교육 용역의 구분과 요구 실적
- 개인정보 처리위탁 여부, 보안 서약·반출입·접근통제 요구사항
- 성과물의 소유권·오픈소스 고지·KRDS 출처 표기 범위
- 실제 접근성 검수 기관, 기준, 검수 시점

기관이 SaaS형 도입을 선택하는 경우에는 [디지털서비스 이용지원시스템](https://www.digitalmarket.kr/)의 등록·심사 제도 적용 가능성도 별도로 검토한다. 이것은 첫 파일럿의 선행 조건이 아니다.

## 7. Go / No-Go 체크리스트

파일럿을 시작하기 전에 아래 모두 `Go`여야 한다.

- [ ] 대상 여정·화면·산출물·수용 기준이 문서로 확정되었다.
- [ ] 입력 데이터의 등급과 외부 AI 입력 금지 범위가 보안·개인정보 담당자에게 승인되었다.
- [ ] 법정·정책 문구의 최종 승인자가 지정되었다.
- [ ] 이 도구가 KRDS 공식 인증 또는 접근성 인증을 대체하지 않는다는 고지가 있다.
- [ ] 공식 KRDS 가이드 버전·URL과 자체 Rule Pack의 버전이 기록된다.
- [ ] 배포 전후 비교를 위한 기준선(VOC, 분석, 과업 테스트 중 하나 이상)을 확보할 수 있다.
- [ ] P0의 명칭·주장·HWP·워드 문서(.docx)·외부 AI 관련 조치가 완료되었다.

하나라도 충족되지 않으면, 생성형 AI가 없는 오프라인 진단·교육 사업으로 범위를 축소하거나 착수를 보류한다.
