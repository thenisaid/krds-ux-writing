# TODO-025 — ET3 데이터 거버넌스 설계 (초안)

> **범위**: 이 문서는 정책 **초안**이다. CC가 초안 문서를 작성할 수는 있지만(Effort: S), 최종 법률·보안 판단은 사용자(프로젝트 관리자)의 몫이다(TODOS.md TODO-025 Effort: M human).
> **전제**: 아직 ET3(이벤트 수집)도 TODO-026(accept 액션 UI)도 구현되지 않았다 — 이 문서는 "짓기 전에" 지켜야 할 설계 제약을 정의한다.
> **근거**: Codex CEO 리뷰(2026-08-20) — "raw 문장 JSON export는 '보안 표면 0'이 아니다." 토큰이 없다고 데이터 자체의 민감도 문제가 사라지지 않는다.

## 1. 기존 보호 장치 — 이미 있는 것 (재확인)

`krds-extension/manifest.json`의 `host_permissions`/`content_scripts.matches`가 이미 기술적 강제를 제공한다:

```json
"matches": [
  "https://thenisaid.github.io/krds-ux-writing/lint.html*",
  "http://localhost:8300/lint.html*",
  "http://127.0.0.1:8300/lint.html*"
]
```

content script는 이 3개 URL에서만 실행된다 — 임의의 실제 공공기관 CMS·게시판 페이지에는 애초에 주입되지 않는다. 이는 원래 Constraints("정부 문서를 외부 AI API로 보내는 것은 법적/보안 리스크")를 만족시키는 **실제 기술적 게이트**이며, "정책 문서로만 선언"이 아니다.

**남은 잔여 위험**: 이 게이트는 "어느 페이지에서 실행되는가"만 막지, "그 페이지에 사용자가 실제로 무엇을 타이핑하는가"는 막지 못한다. 개발자/테스터가 데모 페이지에 실제로 걱정되는 문구(예: 실제 초안의 일부, 이름이 섞인 예시)를 테스트 삼아 붙여넣을 가능성은 기술적으로 차단할 수 없다 — 이 문서가 다루는 건 바로 이 잔여 위험이다.

## 2. ET3가 수집하려는 필드별 민감도 분류

ET3(설계 초안, 미구현)가 다루는 이벤트는 accept/reject/edit 3종이다. 각 필드의 실제 데이터 출처를 확인해 민감도를 분류한다.

| 필드 | 출처 | 민감도 | 근거 |
|------|------|--------|------|
| `event_id`, `timestamp` | 시스템 생성 | 낮음 | 사용자 콘텐츠 아님 |
| `action` (accept/reject/edit) | 사용자 클릭 | 낮음 | 범주값, 자유 텍스트 아님 |
| `rule_id`, `category` (예: `double-passive`, `admin-jargon`) | `krds-lint.js` 고정 규칙 ID | 낮음 | 283개 사전/20개 패턴 중 어느 것에 매치됐는지일 뿐, 사용자 문장 아님 |
| `rule_version`, `dictionary_version` | 시스템 생성 | 낮음 | 버전 문자열 |
| `suggested_alt` | `PATTERN_RULES`/`ADMIN_JARGON`의 **고정** `alt` 필드 (예: "명일까지" → "내일까지") | **낮음** | krds-lint.js 코드 확인 결과 `alt`는 규칙마다 하드코딩된 정적 문자열이지 사용자 입력에서 파생되지 않음 — 로깅해도 사용자 문서 내용이 전혀 드러나지 않는다 |
| `original_snippet` (매치된 구간 원문, 예: "되어지다", 명사 체인 20자) | **사용자가 실제로 타이핑한 텍스트의 일부** | **높음** | 사용자 문서의 실제 단어/구절 — 우연히 이름·기관명·사건 세부사항과 겹칠 수 있음 |
| `edited_text` (향후 TODO-026에서 edit 액션 추가 시, 사용자의 전체 수정문) | **사용자가 직접 작성한 자유 텍스트 전체** | **최고** | 원문/제안문과 달리 완전히 사용자 창작물 — 마스킹 불가능한 자유 형식 |
| `document_context` (주변 문맥) | (설계 계획에 없음) | 해당 없음 | **이번 설계에서 명시적으로 수집 범위 제외** — 매치된 구간 이상은 절대 저장하지 않는다 |

## 3. 정책 결정

### 3.1 수집 범위 — 최소주의

- **저장한다**: `event_id`, `timestamp`, `action`, `rule_id`/`category`, `rule_version`, `suggested_alt`(고정 문자열이므로 그대로)
- **마스킹 후 저장한다**: `original_snippet` — 아래 3.2 참고
- **당분간 수집하지 않는다**: `edited_text`(TODO-026에서 accept UI 자체를 아직 결정 안 함 — "수정" 액션까지 확장할지는 TODO-026 결정 이후 이 정책을 다시 검토), `document_context`(전체 수집 대상에서 영구 제외)

### 3.2 `original_snippet` 마스킹 규칙 — 기술적 강제

정책 선언만으로는 부족하다는 게 이번 리뷰의 핵심 지적이었으므로, 저장 직전 **코드로 강제**하는 마스킹 파이프라인을 명시한다(구현은 ET3 착수 시점, 여기서는 규칙만 확정).

```
1. PII 패턴 검사 (저장 직전 필수 단계, 우회 불가)
   - 전화번호: /01[0-9]-?\d{3,4}-?\d{4}/
   - 이메일: /[\w.+-]+@[\w-]+\.[\w.-]+/
   - 주민등록번호 형식: /\d{6}-?[1-4]\d{6}/
   - 매치되면 해당 부분을 [마스킹됨]으로 치환 (krds-lint.js의 maskNonProseRegions와
     동일한 "같은 자리를 마스킹 문자로 치환" 패턴 재사용 — MASK_CHAR 대신 사람이
     읽을 수 있는 [마스킹됨] 사용, export 파일은 검토자가 직접 읽으므로)

2. 길이 상한 (원문 노출 최소화)
   - original_snippet은 매치된 구간 자체만 저장하고 앞뒤 문맥을 포함하지 않는다
     (이미 설계 계획과 일치 — krds-lint.js의 issue.match가 매치 구간만 반환)
   - 명사 체인 규칙처럼 20자 이상 매치되는 경우 20자로 truncate

3. 저장 위치 강제
   - chrome.storage.local에만 저장 (네트워크 전송 코드 경로 자체를 만들지 않음 —
     ET3 대안 A(서버 릴레이)는 TODO-025/User Challenge 판정에 따라 보류 중이므로
     지금 시점엔 애초에 전송 코드가 없다)
```

**이 마스킹은 옵션이 아니라 저장 함수 자체에 내장한다** — "마스킹할지 말지"를 호출부가 선택하게 두면 다시 "정책은 있지만 기술적 강제가 없다"는 같은 지적을 반복하게 된다.

### 3.3 보존 기간

- `chrome.storage.local`에 최대 30일 보관 후 자동 삭제(생성 시 타임스탬프 기준 조회 시점에 정리) — 개발자 1인 데모 규모에서 무기한 누적을 방지.
- 사용자가 "이력 삭제" 버튼(lint.html에 이미 존재하는 패턴 재사용)으로 언제든 즉시 삭제 가능해야 한다.

### 3.4 Export 시 사용자 확인(consent) 게이트

내보내기 버튼(TODO-025가 전제하는 로컬 배치 export UI, 아직 미구현)은 클릭 즉시 다운로드하지 않고, 아래 확인을 거친다:

```
"이 파일에는 최근 테스트하신 문구의 일부(마스킹 처리됨)가 포함됩니다.
실제 민감한 문서로 테스트하셨다면 파일 내용을 확인 후 공유하세요.
[내보내기] [취소]"
```

이는 마스킹이 100% 완벽하지 않을 수 있다는 전제(3.2의 PII 정규식은 완전하지 않음 — 이름·주소·사건 세부사항 같은 비정형 PII는 정규식으로 다 잡지 못함) 하에, 사람이 마지막 검토자가 되도록 하는 안전망이다.

## 4. 이번 설계로 해결되지 않는 것 (범위 밖, 명시)

- **비정형 PII**(이름, 주소, 사건 세부사항)는 정규식 마스킹으로 완전히 걸러지지 않는다 — 3.4의 사람 확인 게이트가 최후 방어선이다. 완전 자동 익명화는 이번 설계 범위 밖.
- **실제 공공기관 파일럿 배포**는 이 문서의 적용 대상이 아니다 — Constraints에 이미 명시된 대로 별도의 보안 검토(개인정보보호법 검토, 온프레미스 옵션 등)를 거쳐야 하며, 이 정책은 "개발자 로컬 데모" 범위에서만 유효하다.
- **`edited_text`(수정 전체 텍스트) 수집 여부**는 TODO-026(accept UI) 결정 이후 별도로 재검토한다 — 자유 형식 텍스트는 정규식 마스킹으로 방어하기 훨씬 어렵기 때문에, 필요성이 실제로 입증된 뒤에(TODO-024 방식으로) 수집 여부를 다시 판단할 것을 권고한다.
