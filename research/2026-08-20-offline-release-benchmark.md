# 공공기관 1인 PC용 오프라인 배포·벤치마크 조사

> 확인일: 2026-08-20
>
> 대상: `thenisaid/krds-ux-writing`
>
> 목적: 담당자 한 명이 GitHub에서 검증된 설치 파일을 받아 자신의 PC에서만 실행하는 **오프라인 KRDS UX Writing 보조 도구**의 출시 기준을 정한다.
> 성격: 제품·보안·배포 조사 문서다. 법률·개인정보·조달의 최종 판단은 발주기관의 보안, 개인정보, 계약 담당자가 한다.

## 한 줄 결론

첫 기관판은 다음과 같이 한정한다.

> **KRDS UX Writing Assistant Offline** — 입력 문구를 외부로 전송하지 않고, 담당자 PC에서 기관 승인 Rule Pack과 규칙 기반 린트로 문구를 점검하는 데스크톱 도구

GitHub는 **소스와 버전별 설치 파일을 배포하는 곳**으로만 사용한다. 실행 중에는 서버 포트를 열지 않고, 외부 AI·외부 CDN·원문 이력 저장·URL 문구 공유를 기본 제공하지 않는다.

이 결론은 “AI가 없는 축소판”이 아니라 첫 공공기관 도입에서 검증해야 할 가장 중요한 가치—공공언어 규칙의 정확성, 기관별 예외 승인, 담당자의 실제 사용성—를 가장 작은 보안 경계에서 입증하는 순서다.

## 1. 이번 조사에서 확인한 사실

### 1.1 GitHub와 현재 저장소 상태

| 확인 항목 | 확인 결과 | 출시 판단에 주는 의미 |
|---|---|---|
| 원격 저장소 | `https://github.com/thenisaid/krds-ux-writing.git` | GitHub 연결 자체는 되어 있다. |
| 공개 범위 | GitHub API 기준 public | 기관판 코드·문서·릴리스 자산에 비공개 정보가 들어가면 안 된다. 비공개 배포가 필요하면 기관의 승인된 내부 배포 경로를 별도로 쓴다. |
| 로컬 동기화 | `main`이 `origin/main`보다 28개 커밋 앞섬 | 이 28개 커밋은 아직 GitHub에서 내려받거나 Release로 만들 수 없다. 검토 뒤 push와 태그 생성이 먼저다. |
| GitHub Release | 0건 | 설치 파일, 릴리스 노트, 체크섬의 기준점이 아직 없다. |
| 라이선스 | `package.json`에는 MIT이나 최상위 `LICENSE` 파일이 없고 GitHub API도 라이선스를 인식하지 못함 | 공개 배포 전에 저작권자·MIT 전문·제3자 고지의 정리가 필요하다. |
| 테스트 CI | `main` push/PR에서 `npm ci`와 `npm test` 실행 | 좋은 출발점이지만, 설치 패키지 생성·서명·체크섬·SBOM을 검증하는 release 전용 게이트는 없다. |
| 배포 CI | `main` push마다 Vercel Production 배포 | 공개 웹 데모와 기관용 오프라인 설치판은 배포·보안 정책을 분리해야 한다. |

GitHub Release는 태그에 연결된 릴리스 노트와 바이너리 파일을 제공하는 용도에 맞는다. 그러나 GitHub를 사용한다는 사실만으로 설치 파일의 무결성, 서명, 기관 PC에서의 실행 허용, 개인정보 적합성이 자동으로 보장되지는 않는다.

### 1.2 코드·운영 표면 감사

아래는 현재 구현을 읽어 확인한 사항이다. “기능이 나쁘다”는 뜻이 아니라, **온라인 데모/개발용 구조를 기관 오프라인 제품에 그대로 싣지 않아야 한다**는 뜻이다.

| 우선순위 | 확인 내용 | 현재 위치 | 기관판 조치 |
|---|---|---|---|
| P0 | `server.js`가 `0.0.0.0`에 바인딩하고 LAN 주소를 안내한다. | `server.js` | 오프라인 설치판에는 서버를 포함하지 않는다. 내부망 AI PoC가 별도로 필요할 때만 루프백(`127.0.0.1`) 전용 서버를 별도 제품으로 설계한다. |
| P0 | 기본 생성 경로가 Anthropic API이며, 로컬 Ollama는 별도 환경 설정이 필요하다. | `server.js`, `api/`, `functions/api/` | 첫 기관판에서 생성 AI와 해당 API 코드를 UI·패키지에서 제거/비활성화한다. |
| P0 | 검사 뒤 원문 전체를 최대 5건 `localStorage`에 자동 저장한다. | `lint-ui.js` | 기관판은 원문 이력 저장을 기본 제거한다. 필요성이 승인되면 저장 위치·암호화·보존기간·삭제 기능을 별도 설계한다. |
| P0 | 500자 이하 원문을 `?t=` URL에 넣어 복사한다. | `lint-ui.js` | 기관판에서 제거한다. URL은 브라우저 이력·프록시·로그·캡처에 남을 수 있다. |
| P0 | 외부 CDN 폰트·라이브러리를 참조하는 화면이 여러 개다. | HTML 파일 전반 | 설치 패키지는 필요한 정적 자산을 모두 번들에 포함하고 네트워크 요청을 차단한다. |
| P0 | 정적 서버가 `/research/`까지 공개 제공한다. | `server.js` | 기관판에서 연구 문서·개발 산출물은 제품 번들에서 제외한다. |
| P0 | 생성 프롬프트에 공식 명칭과 다른 `Korea Reference Design System` 표기가 있다. | `server.js`, `api/shared/generate-shared.js` | 대외·제품 표현을 공식 명칭 `KoRea Design System` 및 “독립 보조 도구” 고지로 정정한다. |
| P1 | 요청 본문 크기, 인증, 감사·보존 정책은 기관 서버 운영 수준으로 설계돼 있지 않다. | `server.js` | 첫 기관판은 서버 자체를 없애 해결한다. 서버 제품으로 확장할 때 새 보안 설계가 필요하다. |
| P1 | Vercel Production 배포는 테스트 성공과 별개로 `main` push에 연결돼 있고 CLI는 `@latest`다. | `.github/workflows/deploy-vercel.yml` | 웹 데모 워크플로와 제품 release 워크플로를 분리하고, 도구 버전을 고정한다. |
| P1 | `package-lock.json`과 `pnpm-lock.yaml`이 공존한다. | 저장소 루트 | 기관판 빌드는 한 패키지 관리자와 하나의 잠금 파일만 기준으로 재현한다. 현재 CI를 기준으로 하면 npm이 자연스럽다. |
| P1 | Chrome 확장은 지정된 세 개의 자체 린트 URL에서만 동작한다. | `krds-extension/manifest.json` | 현재 확장은 기관 CMS 편집기 통합 제품이 아니다. 첫 설치판의 범위에 포함하지 않고 별도 PoC로 다룬다. |
| P1 | 개발 의존성까지 포함한 감사에서 취약점이 나올 수 있다. | 의존성 트리 | 런타임뿐 아니라 빌드 체인 위험도 매 release마다 판정·기록한다. 자동 수정은 검증 후에만 한다. |

## 2. 권장 배포 구조

### 2.1 두 가지 반입 경로

GitHub에서 사용자가 직접 받는 것이 가능할 때와, 공공기관 망 정책상 GitHub 접근이 안 될 때를 미리 나눠야 한다.

```text
개발·검증 환경
  └─ 승인된 tag / release workflow
       └─ GitHub Release
            ├─ A. 담당자 PC가 GitHub에서 직접 다운로드
            │     └─ 해시·서명 확인 → 설치 → 오프라인 실행
            └─ B. 승인된 담당자가 검증 후 기관 내부 SW 배포함/매체로 반입
                  └─ 담당자 PC 설치 → 오프라인 실행
```

| 경로 | 적합한 경우 | 필수 통제 | 권고 |
|---|---|---|---|
| A. GitHub 직접 다운로드 | 기관 프록시가 `github.com`과 release asset 다운로드를 허용하고 담당자가 외부 파일 반입 승인을 받을 수 있을 때 | 정확한 Release URL, SHA-256, 코드 서명 확인, 다운로드 담당자 기록 | 1인 PC 파일럿의 기본안 |
| B. 내부 배포함/승인 매체 | 인터넷 분리망, GitHub 차단, 중앙 SW 배포 정책이 있을 때 | 반입 전 해시·서명 확인, 원본 Release URL·태그·검증자 기록, 내부 배포본의 재해시 | 보안 요구가 높은 기관의 기본안 |

따라서 “GitHub 내용을 다운로드해야 한다”는 요구는 맞다. 다만 기관이 외부 다운로드를 허용하지 않는 경우에는 GitHub를 **원본 배포처와 추적 기준**으로 삼고, 실제 담당자 PC에는 검증된 파일을 기관 승인 절차로 반입하면 된다. 이때 이메일 첨부나 메신저 재전달처럼 출처·무결성을 잃는 경로는 쓰지 않는다.

### 2.2 실행 구조: 서버가 아닌 데스크톱 앱

권장 구조는 다음과 같다.

```text
Windows 담당자 PC
┌───────────────────────────────────────────────┐
│ KRDS UX Writing Assistant Offline             │
│  ├─ HTML/CSS/JS 번들                           │
│  ├─ 규칙 엔진·공용 사전                         │
│  ├─ 기관 Rule Pack(선택적으로 가져오기)         │
│  ├─ 로컬 파일 열기/저장                         │
│  └─ 네트워크 요청 없음 · 포트 개방 없음          │
└───────────────────────────────────────────────┘
```

현 코드가 HTML/JavaScript 중심인 점을 고려하면, 1차 패키징은 **Electron 기반 Windows 앱**이 가장 현실적이다. Chromium과 런타임을 함께 포함하므로 설치 파일은 크지만, 담당자 PC의 브라우저·Node·로컬 서버 설치를 요구하지 않고 파일 기반 화면을 안정적으로 띄울 수 있다.

### 2.3 구현 방식 비교

| 방식 | 담당자 경험 | 보안·운영 특성 | 현재 코드 전환 비용 | 판단 |
|---|---|---|---|---|
| 단순 HTML ZIP | 압축 해제 후 브라우저로 열기 | 브라우저 정책·파일 접근·외부 자산 의존성 차이가 크고, “설치 제품” 관리가 약하다. | 가장 낮음 | 데모/비상 대안만 |
| `node server.js` | Node 설치 후 URL 접속 | 포트·LAN 노출·AI/API 설정·서버 보안 표면이 생긴다. | 낮음 | 기관 1인 PC 제품에는 부적합 |
| PWA | 설치처럼 보일 수 있음 | 브라우저·서비스워커·업데이트 정책과 인터넷 경로를 별도 관리해야 한다. | 중간 | 공용 웹 도구에는 가능하나 현재 목표에는 차선 |
| **Electron 앱** | 설치 파일을 실행하고 아이콘으로 시작 | 서버 없이 번들 실행 가능. 보안 설정과 코드 서명은 필수이며 파일 크기는 큼. | **중간** | **1차 권고** |
| Tauri 앱 | 작은 설치 파일 가능 | Rust 빌드 체인과 Windows WebView2 배포·검증을 새로 관리해야 한다. | 높음 | Electron 파일럿 성공 뒤 비용 절감 후보 |
| 내부망 웹/AI 서비스 | 다수 담당자가 협업 | 인증·권한·감사·보존·서버 운영·기관 보안 심사가 필요하다. | 매우 높음 | 2단계 이후 |

Electron을 선택해도 “웹 페이지를 앱으로 감싸기만” 하면 안 된다. 공식 보안 가이드에 따라 원격 콘텐츠를 로드하지 않고, `contextIsolation`, sandbox, 엄격한 CSP, 좁은 IPC, 입력 검증을 설계 기준으로 삼는다. 현재처럼 외부 URL을 열거나 Node 권한을 렌더러에 노출하는 방식은 금지한다.

## 3. GitHub Release 설계

### 3.1 첫 Release 자산 목록

처음부터 모든 OS를 지원하려 하지 않는다. 담당자 PC가 Windows라면 Windows x64만 명확하게 지원하고, 다른 OS는 요구가 생긴 뒤 검증한다.

| 자산 | 예시 파일명 | 용도 | 비고 |
|---|---|---|---|
| 기본 설치 파일 | `KRDS-UX-Writing-Assistant-Offline-0.1.0-Setup-x64.exe` | 담당자 직접 설치 | 기관 설치 권한·코드 서명 정책 확인 필요 |
| 휴대용 대안 | `KRDS-UX-Writing-Assistant-Offline-0.1.0-Portable-x64.zip` | 설치가 제한된 PC의 승인된 대안 | 운영 담당자가 압축 해제 위치·업데이트 절차를 정한다. |
| 해시 목록 | `SHA256SUMS.txt` | 다운로드 파일의 변조·오류 확인 | 해시만 함께 받으면 출처 인증은 안 되므로 코드 서명/검증 기록과 함께 쓴다. |
| SBOM | `KRDS-UX-Writing-Assistant-Offline-0.1.0.cdx.json` 또는 `.spdx.json` | 포함된 라이브러리와 버전 확인 | CycloneDX 또는 SPDX 중 하나를 표준으로 고정한다. |
| 릴리스 노트 | GitHub Release 본문 | 변경점·영향·지원 환경·업데이트/롤백 방법 | 기술 용어 대신 담당자가 판단할 수 있는 문장으로 쓴다. |
| 검증 안내 | `VERIFY.md` 또는 Release 본문 | SHA-256·서명·버전 확인 방법 | PowerShell 명령과 예상 값, 서명자 이름을 함께 제공한다. |

MSI는 기관의 중앙 소프트웨어 배포 도구가 이를 요구할 때만 추가한다. “한 담당자 PC가 설치”하는 첫 파일럿에서 EXE, MSI, ZIP을 동시에 운영하면 검증해야 할 조합만 늘어난다. 기본 설치 파일 한 종류와 승인된 ZIP 대안으로 시작한 뒤, 기관 IT 요청이 있으면 MSI를 추가한다.

### 3.2 릴리스 파이프라인

```text
기능 PR
  → 코드 리뷰·테스트
  → main 병합
  → release 후보 tag (예: v0.1.0-offline.1)
  → 깨끗한 CI runner에서 재현 빌드
  → 단위/통합/패키지 스모크 테스트
  → SBOM·SHA-256·provenance 생성
  → Windows 코드 서명 및 서명 검증
  → Draft Release 검토
  → 승인자 publish
  → 담당자 PC 설치 검증 기록
```

Release 워크플로에 반드시 넣을 게이트는 다음과 같다.

1. `npm ci`로 잠금 파일 기반의 깨끗한 설치를 한다.
2. `npm test`와 문법 검사, 패키지된 앱의 실제 실행 스모크 테스트를 한다.
3. 런타임 의존성과 개발·빌드 의존성의 취약점을 각각 기록하고, 예외는 근거·기한·승인자를 남긴다.
4. 제품 번들에 `.env`, API 키, 개인 경로, 연구 원문, 테스트 전용 파일이 들어가지 않는지 검사한다.
5. 네트워크 요청이 없고 포트를 열지 않으며, 외부 CDN이 남지 않았는지 자동 확인한다.
6. SBOM, SHA-256 목록, 빌드 provenance/attestation을 생성한다. GitHub artifact attestation은 이용 가능한 요금제·runner 조건에서 활성화하고 검증 명령을 Release에 남긴다.
7. Windows 설치 파일에는 조직 명의의 Authenticode 코드 서명을 적용하고 `signtool verify`로 검사한다. 코드 서명은 게시자와 무결성을 알리는 장치이며, 그 자체로 모든 실행 경고를 없애거나 보안 승인을 대체하지는 않는다.
8. Release는 자동 공개하지 말고 Draft로 만든 뒤 릴리스 책임자와 기관 파일럿 책임자가 자산·노트·해시를 확인한 후 발행한다.

### 3.3 GitHub 운영 설정

| 항목 | 권고 설정 |
|---|---|
| 기본 브랜치 | `main` 직접 push 대신 PR 병합을 원칙으로 하고, 필수 상태 검사·리뷰를 branch protection에 설정 |
| 태그 | 릴리스 태그 생성 권한을 제한하고, 태그 이름과 설치 파일 버전을 일치 |
| Actions | 현재처럼 SHA로 고정한 action 사용을 유지하고, 추가 action도 commit SHA로 고정 |
| 권한 | 각 workflow의 `permissions`를 최소 권한으로 선언. Release workflow에만 필요한 쓰기 권한 부여 |
| 비밀 | 코드 서명 인증서/비밀번호는 GitHub Secret 또는 별도 HSM·서명 서비스에 보관. 저장소·릴리스 자산·로그에 절대 넣지 않음 |
| 공개 데모 | GitHub Pages/Vercel은 “데모/개발”으로 표시. 기관판 release와 동일 버전인지 혼동시키지 않음 |
| 롤백 | 이전 release를 삭제하지 않고, “권고 중지”와 대체 버전을 릴리스 노트에 명시 |

### 3.4 담당자 설치 흐름

1. 기관의 다운로드/반입 승인 경로에서 Release 버전과 파일명을 확인한다.
2. Release 노트에서 지원 OS, 알려진 제한, SHA-256, 서명자, 데이터 처리 범위를 확인한다.
3. 설치 전 파일 해시와 Windows 서명을 확인한다.
4. 승인된 설치 위치에 설치하고, 시작 화면의 버전이 Release 태그와 같은지 확인한다.
5. 샘플 공개 문구로 린트·Rule Pack 불러오기·결과 저장·네트워크 미사용을 확인한다.
6. 문제 시 원문을 외부에 보내지 않고, 버전·오류 코드·비내용 화면 캡처만 지원 창구로 전달한다.
7. 업데이트는 자동 설치가 아니라 새 Release의 검증을 마친 뒤 수동으로 한다. 이전 설치 파일을 보관해 롤백한다.

PowerShell 검증 예시는 Release에 실제 해시 값과 함께 제공한다.

```powershell
Get-FileHash .\KRDS-UX-Writing-Assistant-Offline-0.1.0-Setup-x64.exe -Algorithm SHA256
Get-AuthenticodeSignature .\KRDS-UX-Writing-Assistant-Offline-0.1.0-Setup-x64.exe
```

## 4. 오프라인 보안·개인정보 설계 기준

### 4.1 출시 차단 조건

아래 중 하나라도 남아 있으면 기관판 Release를 만들지 않는다.

- 앱 실행 중 외부 API, 외부 폰트/CDN, 분석·광고 endpoint로 요청이 나간다.
- API 키, `.env`, 내부 URL, 개인 파일 경로, 샘플 외 실제 기관 문구가 번들·로그·Release 자산에 포함된다.
- 원문이 자동으로 `localStorage`, 파일, URL, 클립보드 이외 위치에 저장되거나, 저장 사실·삭제 방법이 사용자에게 보이지 않는다.
- 로컬 서버가 LAN 또는 모든 인터페이스에 열리거나, 의도하지 않은 포트를 사용한다.
- 설치 파일의 버전, SHA-256, 서명, SBOM 중 하나라도 확인할 수 없다.
- 라이선스와 KRDS·제3자 저작물의 사용 고지가 확정되지 않았다.
- 파일럿 담당자가 설치 권한, 업데이트 담당, 장애 연락처를 알지 못한다.

### 4.2 최소 데이터 정책

| 데이터 | 첫 기관판 정책 | 이유 |
|---|---|---|
| 입력 원문 | 메모리에만 두고 앱 종료 시 폐기 | 사용자가 붙여넣은 문구에도 개인정보·비공개 정보가 섞일 수 있다. |
| 검사 결과 | 사용자가 명시적으로 저장/복사한 것만 생성 | 자동 기록·분석을 피한다. |
| Rule Pack | 기관이 승인한 JSON/파일만 가져오기 | 규칙·예외·승인 버전을 추적하되 민원 원문과 분리한다. |
| 사용 통계 | 수집하지 않음 | 첫 출시의 목적은 품질 도구 검증이지 사용자 감시가 아니다. |
| 오류 로그 | 기본적으로 원문 미포함. 버전·오류 코드·기능명만 선택적 저장 | 지원에 필요한 최소 정보만 남긴다. |
| 업데이트 확인 | 자동 요청하지 않음 | 망 정책과 의도하지 않은 외부 통신을 피한다. |

개인정보보호법 검토는 “PC 밖으로 전송하지 않으니 필요 없다”로 끝나지 않는다. 기관의 데이터 분류, 접근 권한, 보존·삭제, 이동식 매체 반입 정책이 적용될 수 있으므로, 첫 파일럿은 공개 화면 문구와 비식별 테스트 문구만으로 시작한다.

### 4.3 Electron 보안 체크리스트

- `BrowserWindow`에서 `nodeIntegration: false`, `contextIsolation: true`, sandbox 활성화를 기본값으로 한다.
- 앱 내부의 정적 HTML만 로드하고 임의 URL 탐색, `new-window`, 외부 프로토콜 호출을 차단한다.
- renderer와 main process 사이에는 필요한 동작만 노출한 preload API를 두고, 모든 파일 경로와 입력을 검증한다.
- CSP는 `default-src 'self'`를 기본으로 하며 `unsafe-eval`, 원격 script, 원격 font를 넣지 않는다.
- `shell.openExternal`은 허용 목록이 있는 도움말 URL 등 필요한 경우에만 쓴다.
- Rule Pack import는 파일 형식·크기·스키마를 검사하고, 가져온 규칙을 실행 코드로 해석하지 않는다.
- 빌드 전후 네트워크 감시 테스트로 `http://`, `https://`, websocket 요청이 없는지 확인한다.
- 설치 패키지에는 제품 실행에 필요한 파일만 포함하고 개발 문서, 서버, API handler, 테스트, `.git`은 제외한다.

### 4.4 왜 URL 공유를 제거하는가

GOV.UK UI Writing 가이드도 개인 정보를 URL에 넣지 않도록 안내한다. 이 프로젝트의 현재 `?t=` 공유는 500자 제한이 있어도 원문을 URL·브라우저 이력·프록시 로그·스크린샷에 남길 수 있다. “공개 문구만 넣으세요”라는 고지만으로는 실수 경로를 막지 못하므로, 기관 오프라인 제품에는 기능 자체를 싣지 않는 것이 맞다.

### 5.3 벤치마크 검증 과제

벤치마크는 사이트를 많이 보는 것으로 끝나면 안 된다. 첫 파일럿 전에 공개·비식별 문구로 다음 표본을 만든다.

| 표본군 | 최소 포함 화면 | 평가 질문 |
|---|---|---|
| 신청·자격 | 자격 판단, 단계 안내, 제출 | 대상·기한·필수 자료·다음 행동이 드러나는가? |
| 입력·첨부 | 레이블, 도움말, 형식 오류 | 무엇을 왜 어떻게 입력하는지 알 수 있는가? |
| 오류·복구 | 인증 실패, 시스템 오류, 제출 실패 | 상황·가능한 이유·복구 행동이 있고 사용자를 탓하지 않는가? |
| 완료·상태 | 접수 완료, 처리 중, 보완 요청, 결과 | 완료 사실·예상 일정·확인 경로·후속 행동이 있는가? |
| 고위험 용어 | 법정·금융·복지·의료·사법 용어 | 무리한 치환 없이 풀어쓰기·병기·도움말이 제안되는가? |

정확도는 점수 하나가 아니라 아래로 본다.

- 규칙별 정탐률: 실제로 고쳐야 하는 문구를 잡은 비율
- 오탐률: 법정·기관 고유 용어를 부당하게 경고한 비율
- 제안 수용률: 담당자가 검토 후 채택한 비율과 거절 사유
- 심각도 적합성: 오류·경고·정보 분류가 실제 사용자 영향과 맞는지
- 과업 결과: 개선 전후 이해도, 완료율, 문의/VOC 변화

기존 `research/public-service-corpus.md`와 `research/public-service-survey-expanded.md`의 시민 과업 표본은 이 검증 세트를 만들기 위한 출발점으로 사용한다. 실제 민원 원문이나 개인정보가 있는 화면을 무단 수집해 벤치마크 데이터로 만들지 않는다.

## 6. 사전·Rule Pack 거버넌스

### 6.1 공통 사전과 기관 사전의 분리

```text
공통 규칙
  ├─ 명확한 행정어·문체 패턴
  ├─ 공개 근거와 테스트
  └─ 모든 기관에서 같은 뜻을 유지할 수 있는 항목

기관 Rule Pack
  ├─ 법정·정책 용어와 첫 등장 병기 방식
  ├─ 기관 고유 서비스명·상태값·예외
  ├─ 승인자·근거·만료일
  └─ 화면/컴포넌트별 심각도 조정
```

공통 사전은 작은 대신 신뢰도가 높아야 한다. 불확실한 용어를 많이 넣으면 린터는 “도움”보다 “무시되는 경고”가 된다. 기관 특화 판단은 기존 [기관 UX Writing Rule Pack 템플릿](./agency-rule-pack-template.md)으로 분리해, 승인·예외·재검토일을 남긴다.

### 6.2 MCST 보류 후보 처리 결론

현재 `research/mcst-terms-candidates.md`에서 미선택 상태인 항목은 **8개**다. 이들은 공통 자동 치환 사전에 넣지 않고, 기관별 요구가 있을 때만 Rule Pack 후보로 검토한다.

| 후보 | 공통 사전 처리 | 이유 |
|---|---|---|
| 베이비 페어 | 제외 | 행사·마케팅 맥락 의존 표현이다. |
| 베이비 플래너 | 제외 | 실제 직무·서비스명·마케팅 명칭의 맥락이 다르다. |
| 사이버 론 | 제외 | 금융 상품·법정 설명에서 정확한 명칭과 조건을 보존해야 한다. |
| 소셜 워커 | 제외 | 제안 대체어 중 의미가 부정확하거나 직종 명칭과 충돌할 수 있다. |
| 아이에스에이(ISA) | 제외 | 금융상품의 정식 약어로, 첫 등장 풀어쓰기 규칙이 더 적절하다. |
| 패키지 딜 | 제외 | 제안된 “일괄 신고”는 일반적 의미 대체어가 아니다. |
| 펠로십 | 제외 | 연구 지원금·연구자 과정·직위 등 의미가 갈린다. |
| 폴리슈머 | 제외 | 통용 의미와 제안 대체어의 관계가 불안정하다. |

이 결정은 원본 데이터의 가치를 부정하는 것이 아니다. “쉬운 우리말” 후보는 참고 데이터이며, 공통 규칙으로 승격하려면 공공서비스 문맥, 의미 보존, 대체 표현의 자연스러움, 오탐 위험을 모두 통과해야 한다.

## 8. Go / No-Go 체크리스트

### Go 조건

- [ ] 기관 담당자 PC의 Windows 버전·설치 권한·외부 다운로드/반입 경로가 확인됐다.
- [ ] GitHub에 검토된 커밋이 push되고, 정확한 tag와 Draft Release가 생성됐다.
- [ ] 설치 파일의 버전·SHA-256·코드 서명·SBOM을 확인했다.
- [ ] 앱은 네트워크 요청이나 포트 개방 없이 실행한다.
- [ ] 원문은 기본 자동 저장되지 않고 URL에 들어가지 않는다.
- [ ] 외부 AI 호출과 API 키 경로가 기관판에 없다.
- [ ] 공통 사전·기관 Rule Pack의 승인자·예외·확인일이 있다.
- [ ] KRDS 공식 인증·접근성 인증을 대체하지 않는다는 고지가 제품과 Release에 있다.
- [ ] 설치·사용·업데이트·삭제·롤백을 담당자 한 명이 문서만 보고 수행했다.

### No-Go 조건

- [ ] “로컬 실행”이라는 이유만으로 실제 민원 원문·개인정보의 입력을 허용하려 한다.
- [ ] GitHub Release가 아닌 임의 ZIP·이메일 첨부본을 설치하려 한다.
- [ ] 서명·해시·버전·릴리스 노트 중 하나가 빠졌다.
- [ ] Vercel/외부 API/외부 CDN을 끌 수 없거나 그 동작을 증명하지 못한다.
- [ ] 법정·정책 문구를 린터가 자동으로 바꾸고 사람 승인 경로가 없다.

## 9. 다음 의사결정

이 조사 뒤 바로 결정할 것은 세 가지다.

1. **배포 모델:** 첫 파일럿을 Windows x64 Electron 설치판 + portable ZIP으로 고정할지
2. **반입 경로:** GitHub 직접 다운로드가 가능한지, 아니면 기관 내부 반입 경로를 기본으로 할지
3. **첫 범위:** AI 없이 규칙 린트와 기관 Rule Pack만으로 시작할지

현 조건(공공기관, 담당자 1명 PC, 외부 전송 최소화)에서는 세 항목 모두 `예`가 가장 안전하고 실행 가능하다. 이 결정을 받으면 다음 구현 단계는 “기존 웹 데모를 더 고치는 것”이 아니라, **기관판 전용 패키지와 Release workflow를 새로 만드는 작업**이 된다.
