# KRDS UX Writing 공공기관 오프라인 제품·사업 종합 감사 및 벤치마크

> 조사일: 2026-08-20<br>
> 대상: thenisaid/krds-ux-writing 저장소와 그 공개 배포 경로<br>
> 의사결정 대상: 공공기관 담당자 한 명의 Windows PC에서 사용하는 오프라인 문구 품질 도구<br>
> 성격: 기술·보안·운영·시장·사업성의 사전 검토 문서다. 법률, 개인정보, 조달, 접근성 인증 및 기관 보안의 최종 판단은 해당 기관의 담당 부서와 계약 절차에 따른다.

## 결론부터

### 현재 결정

| 결정 | 판단 | 뜻 |
|---|---|---|
| 현재 저장소를 그대로 기관에 배포 | No-Go | 웹 데모, AI 생성기, 서버, 연구 자료, Chrome 확장과 제안서가 한 저장소에 섞여 있어 기관 오프라인 설치판의 경계가 없다. |
| 오프라인 제품으로 전환하는 투자 | 조건부 Go | 외부 전송 없는 규칙 기반 린트와 기관 Rule Pack만을 첫 범위로 고정하면, 90일 내 1인 PC 파일럿을 검증할 만한 기반이 있다. |
| 외부 생성형 AI를 첫 기관판에 포함 | No-Go | 현재 기본 경로는 Anthropic API를 사용할 수 있고, 기관 입력 문구의 외부 전송 여부가 제품 경계에서 차단되지 않는다. |
| GitHub를 배포 원본으로 사용 | Go, 통제 조건부 | GitHub Release를 원본·추적 기준으로 쓰되, 설치 파일의 서명·해시·SBOM·승인된 반입 절차를 갖춰야 한다. |
| 당장 SaaS 또는 범용 AI Writer로 판매 | No-Go | 보안 경계, 운영 체계, 고객 데이터, 정확도와 지불의사 검증이 아직 없다. |
| 서비스 주도 파일럿으로 시장 검증 | Go | 진단, 기관 Rule Pack, 오프라인 린터, 교육과 운영 거버넌스를 묶은 작은 파일럿이 가장 현실적인 첫 수익·학습 경로다. |

권장 제품 정의는 다음 한 문장으로 제한한다.

> KRDS UX Writing Assistant Offline은 외부로 원문을 전송하지 않고, 담당자 PC에서 공통 규칙과 기관 승인 Rule Pack으로 공공서비스 문구를 점검하는 독립 보조 도구다.

이 제품은 공식 KRDS, 접근성 인증, 법정 문구 검토 또는 기관의 최종 품질 판정을 대체하지 않는다. 공식 KRDS 적용 과정에서 문구 품질을 반복 점검하고, 기관별 예외와 검토 이력을 남기게 하는 품질 게이트다.

## 1. 조사 범위와 방법

### 1.1 전제

- 실제 사용자는 공공기관 담당자 한 명이며, Windows PC에서 설치 후 실행한다.
- GitHub는 소스와 검증된 Release 자산의 원본 배포처다. 기관망이 GitHub를 막으면, 승인 담당자가 검증한 같은 자산을 내부 소프트웨어 배포함 또는 승인 매체로 반입한다.
- 설치 이후 기본 동작은 오프라인이다. 외부 AI, 외부 CDN, 분석, 자동 업데이트, 자동 원문 이력은 첫 기관판의 범위가 아니다.
- 파일럿에는 공개 화면 문구 또는 기관이 승인한 비식별 테스트 문구만 사용한다. 민원 원문, 개인정보, 민감정보, 비공개 업무·보안 정보는 입력하지 않는다.
- Codex 로그인은 이 제품의 설치·실행·배포 조건이 아니다. 내부 서버 우회 환경이라는 전제를 바꾸지 않는다.

### 1.2 확인한 방법

| 구분 | 수행 내용 | 한계 |
|---|---|---|
| 저장소 감사 | 코드, 구성, 워크플로, 문서, npm 패키지 후보를 읽고 실행 경계를 추적했다. | 기관의 실제 망 정책·서명 인증서·Windows 설치 권한은 아직 확인하지 않았다. |
| 품질 검증 | 2026-08-20 기준 npm test와 unpacked Chrome 확장의 실제 브라우저 검증 기록을 확인했다. | 이는 Electron 설치 파일의 E2E나 실제 기관 CMS 검증은 아니다. |
| 공급망 확인 | GitHub 공개 메타데이터, Release 유무, 라이선스 파일, npm pack dry run, 의존성 감사 상태를 확인했다. | 서명 키·HSM·조직 계정의 실제 설정은 확인 대상이 아니다. |
| 데스크 리서치 | KRDS, 법령, GitHub, Electron, Microsoft, CISA와 해외 공공 콘텐츠·콘텐츠 거버넌스 제품의 공식 자료를 확인했다. | 각 자료의 최신 개정·계약 적용성은 발주 직전에 다시 확인해야 한다. |
| 사업 검토 | 제품의 현재 기능, 공공기관 도입 절차, 비교 제품의 운영 모델을 교차해 고객·채널·가설을 도출했다. | 시장 규모나 가격은 독립적인 고객 인터뷰·견적·조달 검토 없이 확정하지 않는다. |

이 문서의 외부 근거 링크는 마지막 참고 자료에 모았다. 경쟁사의 마케팅 문구는 기능의 존재를 이해하기 위한 참고이지, 보안성이나 공공기관 적합성의 보증 근거가 아니다. 코드·배포·테스트의 세부 증거와 미확인 범위는 [감사 증거 매트릭스](./2026-08-20-audit-evidence-matrix.md)에 분리해 기록했다.

## 3. 출시 차단 감사

### 3.1 P0: 외부 배포 또는 실제 기관 문구 입력 전에 해결

| 항목 | 증거 | 위험 | 필수 조치 | 완료 증거 |

| 공급망 무결성 부재 | GitHub Release가 없고, 설치 파일·서명·SHA-256·SBOM·provenance 체계가 없다. | 담당자가 받은 파일의 출처와 변조 여부를 확인할 수 없다. | 태그 기반 Draft Release, SHA-256, SBOM, Windows 코드 서명, 검증 문서를 release workflow로 만든다. | 깨끗한 runner에서 만든 자산의 서명·해시·SBOM을 검증한다. |
| 대외 주장 리스크 | B2G 문서에 KRDS 고시, 나라장터 규격, KWCAG 100%, 고정 품목·계약·지급 조건 같은 표현이 있다. | 사실과 다른 조달·인증·계약 주장으로 신뢰·법적 문제가 생긴다. | 해당 문서는 대외 사용을 중지하고, 발주별 최신 기준과 담당자 확인 전에는 가정·예시로도 제시하지 않는다. | 수정본에 근거, 적용 범위, 책임 주체, 확인일이 있다. |

| 항목 | 현재 관찰 | 권장 조치 |
|---|---|---|
| 버전 체계 | package.json 0.1.0, VERSION 0.1.0.2, lint UI와 확장 1.0.0, prompt library v2.0 등 여러 표기가 공존한다. | 하나의 제품 버전 규칙을 정한다. tag, 설치 파일, 앱 정보, 릴리스 노트, SBOM을 같은 버전으로 묶는다. |
| Node·잠금 파일 | package.json은 Node 14 이상이지만 Vitest 4와 Vite 8은 더 높은 Node를 요구한다. package-lock과 pnpm-lock은 서로 다른 Vitest·Vite 버전을 가리킨다. | npm과 package-lock을 단일 기준으로 정하고 engines를 실제 CI 지원 버전으로 올린다. |
| 웹 데모 자동 배포 | main push가 Vercel Production 배포로 이어지고 Vercel CLI는 latest를 설치한다. | 공개 데모와 기관 Release 워크플로를 분리하고, 도구 버전을 고정하며, 기관판은 승인자가 Draft Release를 발행한다. |
| 환경별 API 차이 | Vercel, Cloudflare, local server가 서로 다른 rate limit·실행·보안 동작을 가진다. | AI PoC는 별도 프로젝트·문서·보안 모델로 분리한다. 기관판에는 이 코드를 포함하지 않는다. |
| Rule Pack 기능 공백 | 템플릿은 있으나 기관 JSON의 import, 스키마 검증, 버전·승인·예외 적용 기능은 없다. | 최소 스키마, 파일 크기 제한, JSON schema 검증, 변경 이력, 읽기 전용 승인본을 구현한다. |
| 설치 패키지 QA | 단위 테스트는 강하지만 Windows 설치, 삭제, 재설치, 오프라인 실행, 업데이트·롤백 검증은 없다. | 실제 Windows VM에서 설치·실행·종료·파일 import·삭제·롤백을 자동/수동으로 점검한다. |
| 보안 취약점 triage | npm audit의 런타임 의존성은 0건이지만 개발 의존성 경로에는 nanoid·postcss 관련 high 2건이 관찰된다. | 무조건 자동 업데이트하지 말고 영향 분석, 잠금 파일 갱신, 전체 테스트, 예외 승인 기록을 release 게이트에 넣는다. |
| 문서 정확도 | TESTING 문서의 Vitest 버전과 E2E 상태가 실제와 어긋나는 부분이 있다. | 지원 환경, 테스트 범위, 알려진 제한을 실제 CI·설치판 결과에 맞춰 갱신한다. |
| 사전 수치 설명 | 공개 사전은 283개지만 런타임 규칙은 오류 메시지 inline 규칙을 포함해 290개다. | 283개 공통 사전 + 7개 고정 오류 규칙처럼 정확히 설명하거나, 데이터 모델을 하나로 통일한다. |

### 3.3 P2: 파일럿의 효과가 확인된 뒤

- MSI와 기관 중앙 소프트웨어 배포 도구 연동
- macOS 또는 다른 CPU 아키텍처 지원
- 기관 CMS, Figma, 문서 편집기와의 실제 통합
- 승인된 내부망 LLM 또는 별도 AI 게이트웨이
- 다기관 계정, SSO, 권한, 감사, 보존·삭제, 지원 SLA
- 자동 업데이트와 취약점 패치 채널
- 다기관 Rule Pack 마켓 또는 템플릿 라이브러리

P2는 첫 기관판을 작게 만드는 이유다. P2의 운영 통제를 P0로 미루지 않고, 파일럿에서 가치와 책임 주체가 확인된 뒤에 투자한다.

## 4. 권장 기술·배포 구조

### 4.1 GitHub의 역할

GitHub는 실행 환경이 아니라 원본·이력·검증된 배포 자산의 기준점이다.

    개발·검증
        → 승인된 tag
        → 깨끗한 CI에서 재현 빌드·테스트
        → 서명·SBOM·SHA-256 생성
        → GitHub Draft Release
        → A. 담당자 PC가 직접 다운로드 후 검증
          또는
        → B. 승인 담당자가 기관 내부 배포함·매체로 반입 후 재검증
        → 담당자 PC에서 오프라인 실행

담당자 PC가 GitHub에 접근할 수 있으면 A를 쓴다. 망 분리·차단 또는 기관의 외부 반입 정책이 있으면 B를 쓴다. 두 경우 모두 이메일 첨부, 메신저 전달, 임의 ZIP 재압축처럼 원본 tag·해시·서명·검증 기록을 끊는 경로는 쓰지 않는다.

현재 main은 origin/main보다 28개 커밋 앞서 있다. 이 상태에서는 해당 변경분을 외부에서 내려받거나 Release로 만들 수 없다. 코드와 문서 검토가 끝난 뒤 push, tag, Draft Release의 순서가 필요하다.

### 4.2 첫 구현 선택

| 방식 | 판단 | 이유 |
|---|---|---|
| 단순 HTML ZIP | 비상 데모 대안 | 설치가 필요 없지만 브라우저 정책·파일 권한·외부 자산·업데이트를 통제하기 어렵다. |
| node server.js | 제외 | Node 설치, 포트, LAN 노출, AI/API 설정이라는 불필요한 운영 표면이 생긴다. |
| PWA | 차선 | 공용 웹 서비스에는 가능하나 서비스워커·브라우저·업데이트 경로를 별도로 운영해야 한다. |
| Electron Windows 앱 | 1차 권고 | 현재 HTML/JS를 재사용하면서 서버 없이 아이콘으로 실행하는 설치판을 만들 수 있다. 파일 크기와 코드 서명 비용은 감수한다. |
| Tauri | 2차 후보 | 더 작은 배포물은 가능하나 Rust·WebView2·Windows 빌드 검증을 새로 운영해야 한다. |
| 내부망 웹·AI 서비스 | 2단계 이후 | 다수 사용자에게는 적합할 수 있으나 인증·권한·감사·보존·서버 보안 심사가 필요한 다른 제품이다. |

Electron을 택한다면 원격 URL을 로드하지 않고, nodeIntegration false, contextIsolation true, sandbox, 좁은 preload API, 허용 목록 기반 외부 열기, 엄격한 CSP를 설계 기준으로 한다. 이것은 단순히 HTML을 감싸는 작업이 아니다.

### 4.3 릴리스 최소 자산

| 자산 | 목적 | 첫 Release 원칙 |
|---|---|---|
| Windows x64 설치 파일 | 담당자 PC 설치 | 기본 배포물 하나로 시작한다. |
| Portable ZIP | 설치 권한이 제한된 경우의 승인된 대안 | 기관 요청이 있을 때만 함께 제공한다. |
| SHA256SUMS | 다운로드 오류·변조 확인 | Release 본문에도 실제 값과 확인 방법을 쓴다. |
| SBOM | 포함 라이브러리·버전 확인 | CycloneDX 또는 SPDX 중 하나로 고정한다. |
| 릴리스 노트 | 변경, 제한, 지원 환경, 업데이트·롤백 설명 | 기술팀이 아닌 담당자가 읽을 수 있게 쓴다. |
| VERIFY 안내 | 해시와 Authenticode 서명 확인 | 예상 해시값과 서명자 이름을 함께 제공한다. |

MSI는 기관의 중앙 배포 도구가 요구할 때 추가한다. 첫 1인 PC 파일럿에 EXE, MSI, ZIP을 모두 같은 수준으로 운영하면 검증해야 할 조합만 증가한다.

### 4.4 배포 게이트

1. 단일 잠금 파일을 기준으로 깨끗한 CI runner에서 재현 빌드한다.
2. 단위·통합 테스트와 패키징된 앱의 Windows 스모크 테스트를 실행한다.
3. 번들에 API 키, 환경 파일, 개인 경로, 연구 원문, 테스트, 서버, AI 코드가 없는지 allowlist 검사한다.
4. 앱 실행 동안 HTTP(S), WebSocket, DNS 요청과 리스닝 포트가 없는지 검사한다.
5. SBOM, SHA-256, provenance를 생성하고 설치 파일에 Authenticode 서명을 적용한다.
6. Draft Release에서 제품 책임자와 파일럿 책임자가 자산·해시·서명·노트를 검토한다.
7. 공개·내부 배포 전에 비내용 샘플로 설치·검사·Rule Pack import·종료·삭제·롤백을 실제 담당자가 문서만 보고 수행한다.

자세한 배포·보안 설계는 별도 조사 문서인 2026-08-20-offline-release-benchmark.md를 기준으로 한다.

## 5. 시장과 고객: 무엇을 팔 것인가

### 5.1 문제 정의

공공서비스의 문구 문제는 맞춤법 문제가 아니다. 서비스 화면마다 업무 규칙·법정 용어·브랜드·접근성·사용자 과업이 만난다. 팀이 바뀌거나 개편이 반복될수록 같은 개념이 여러 이름으로 쓰이고, 오류·완료·기한 안내가 불완전하며, UX와 업무 부서가 수정의 근거를 공유하기 어려워진다.

따라서 고객이 사는 것은 AI가 만든 문장이 아니라 다음 결과다.

- 핵심 여정의 문구 인벤토리와 우선순위
- 기관 법정·정책 용어를 훼손하지 않는 승인된 예외
- 버튼·입력폼·오류·완료 상태의 반복 가능한 규칙
- 누가 무엇을 왜 승인했는지 남는 개선 시트
- 외부 전송 없이 담당자가 수시로 쓰는 최소 점검 도구

### 5.2 권장 포지셔닝

| 선택지 | 판단 | 이유 |
|---|---|---|
| 범용 한국어 AI Writer | 비권고 | 대형 모델·SaaS와 기능 경쟁이 되고, 공공기관 보안·책임 문제에서 약하다. |
| 맞춤법 검사기 | 비권고 | 기존 대안과의 차별과 가격 근거가 약하다. |
| KRDS 인증 도구 | 금지 | 공식 인증 권한과 검수 범위를 넘어선다. |
| 공공 UX Writing Quality Gate | 권고 | KRDS 적용, 기관 Rule Pack, 상태 문구, 검토 이력, 오프라인 경계를 하나의 문제로 묶는다. |
| 서비스+도구 하이브리드 | 첫 시장 권고 | 기술만 판매하기보다 진단·Rule Pack·교육으로 신뢰와 데이터를 쌓을 수 있다. |

핵심 문구:

> 공식 KRDS 적용을 보조하는, 기관별 문구 품질 운영 도구

공격적인 표현인 KRDS의 부족함을 채운다, KRDS보다 낫다, 공식 기준을 자동으로 준수한다는 쓰지 않는다.

### 5.3 초기 고객과 사용자

| 구분 | 가장 적합한 대상 | 필요한 가치 | 피해야 할 첫 대상 |
|---|---|---|---|
| 구매·스폰서 | 기관 디지털서비스 PM, UX 책임자, 정보화·개편 사업 책임자 | 개편 품질과 검수 증빙, 반복 비용 감소 | 단독 콘텐츠 담당자에게 전사 도입을 즉시 판매 |
| 실사용자 | 콘텐츠·UX·디자인·개발·QA 담당자 | 빠른 사전 점검, 일관된 기관 예외, 복사 가능한 개선안 | 업무·법정 문구 책임자 없이 자동 수정 |
| 협업자 | 업무 부서, 법무·정책, 접근성, 보안·개인정보 담당 | 검토 경계와 승인 이력 | 도구가 이들의 최종 판단을 대체한다는 구조 |
| 파트너 | KRDS 개편 SI, UX 컨설팅, 접근성 검수·교육 파트너 | 문구 품질 레이어와 재사용 가능한 산출물 | 무차별 리셀러·공공조달 대행 약속 |

첫 파일럿 후보는 공개 문구 중심의 문화·교육·예약·지원사업 안내 흐름이다. 민원, 세무, 의료, 상담, 복지 급여처럼 민감도·법정 정확도·개인정보 위험이 높은 흐름은 첫 사용처에서 제외한다.

### 5.4 서비스 주도 상업 모델

초기에는 구독 가격표보다 발견과 검증을 파는 편이 낫다.

| 단계 | 고객이 받는 것 | 제품이 배우는 것 | 상업적 의미 |
|---|---|---|---|
| 0. 2주 진단 | 화면·문구 인벤토리, 위험도, 개선 기회, 데이터 경계 | 실제 고통, 문구량, 승인 병목, 구매자 | 유료 또는 낮은 진입비의 발견 단계 |
| 1. Rule Pack 설계 | 용어·예외·상태 문구·승인 매트릭스, Before/After 시트 | 기관별 차이와 공통화 가능한 규칙 | 가장 먼저 상품화할 전문 서비스 |
| 2. 오프라인 도구 파일럿 | 1인 PC 설치판, 교육, 수동 업데이트·지원 절차 | 사용 빈도, 오탐, 수용률, 설치 장벽 | 제품 적합성 검증 |
| 3. 운영 거버넌스 | 분기 Rule Pack 리뷰, 신규 화면 점검, 교육, 성과 보고 | 갱신·지원 비용과 연간 수요 | 반복 수익과 사례 축적 |

고정 가격, 조달 품목 코드, 수의계약 기준, 지급 조건을 지금 정해 공개하지 않는다. 기관의 계약 유형, 범위, 투입 인력, 보안 요구, 최신 조달 기준에 따라 달라지기 때문이다. 실제 견적은 법무·조달 검토를 거친 개별 제안에서만 낸다.

### 5.5 구매 논리와 채널

| 채널 | 들어가는 방법 | 초기 제안 | 성공 신호 |
|---|---|---|---|
| 기존 KRDS·홈페이지 개편 사업 | SI·UX 파트너와 문구 품질 워크스트림으로 결합 | 핵심 여정 1개 진단과 Rule Pack | RFP 또는 산출물에 문구 검수·운영 항목이 들어간다. |
| 기관 UX·콘텐츠 팀 | 공개 화면 기반 워크숍 | 오류·완료·CTA 샘플 개선과 오프라인 도구 체험 | 업무·UX 책임자가 공동 파일럿을 요청한다. |
| 접근성·사용성 진단 연계 | 독립 검수 대체가 아닌 사전 문구 검토 보조 | 레이블·오류·상태 전달의 문구 점검표 | 접근성 검수 전 반복 사용이 발생한다. |
| 교육 | 공무원·수행사 실무 교육 | 기관 실제 공개 문구를 이용한 Rule Pack 워크숍 | 교육 후 자가 점검과 개선 요청이 이어진다. |

### 5.6 방어력의 원천

기술 그 자체는 쉽게 복제될 수 있다. 방어력은 다음을 축적할 때 생긴다.

1. 출처·근거·확인일이 있는 한국 공공서비스 문구 규칙
2. 기관별 법정 용어와 예외를 안전하게 운영한 Rule Pack 설계 방법
3. 오류·상태·완료·기한 등 컴포넌트별로 축적된 승인 사례
4. 오탐·수용률·과업 성공을 포함한 검증 데이터
5. 보안·배포·변경관리까지 이해하는 공공 도입 레퍼런스

즉, 비공개 원문 코퍼스를 무분별하게 모으는 것이 아니라, 승인된 공개·비식별 사례와 규칙의 근거·판단 이력을 자산으로 만든다.

## 7. 검증 가설과 파일럿 설계

### 7.1 검증할 가설

| 가설 | 왜 중요한가 | 측정 방법 |
|---|---|---|
| 공통 규칙은 사람이 검토할 가치가 있는 문제를 충분히 잡는다. | 규칙 엔진이 일상 사용의 출발점인지 확인한다. | 규칙별 정탐률, 심각도 적합성, 오탐 사유 |
| 기관 Rule Pack은 법정·고유 용어의 불필요한 경고를 줄인다. | 공공기관 수용성을 좌우한다. | 승인 용어 오탐률, 예외 적용 성공률, 검토 시간 |
| 오프라인·무저장 기본값은 도입 장벽을 낮춘다. | 외부 AI 대비 차별과 보안 경계다. | 보안·개인정보 담당자의 요구사항 충족 여부, 설치 승인 속도 |
| 오류·상태·완료 문구의 규칙은 실제 과업 이해를 개선한다. | 단순 점수 대신 사용자 결과를 본다. | 전후 과업 완료율, 이해도, 실패·문의 유형 |
| 서비스+도구 모델에 반복 수요가 있다. | 제품화와 수익성의 근거다. | 진단 후 Rule Pack/교육/운영 계약 전환율, 재사용 화면 수 |

### 7.2 최소 검증 표본

| 표본군 | 최소 화면 유형 | 반드시 보는 질문 |
|---|---|---|
| 신청·자격 | 자격 판단, 단계 안내, 제출 | 대상, 기한, 필수 자료, 다음 행동이 보이는가 |
| 입력·첨부 | 레이블, 도움말, 형식 오류 | 무엇을 왜 어떻게 입력하는지 알 수 있는가 |
| 오류·복구 | 인증 실패, 시스템 오류, 제출 실패 | 상황, 가능한 이유, 복구 행동이 있고 사용자를 탓하지 않는가 |
| 완료·상태 | 접수 완료, 처리 중, 보완 요청, 결과 | 완료 사실, 예상 일정, 확인 경로, 후속 행동이 있는가 |
| 고위험 용어 | 법정, 금융, 복지, 의료, 사법 용어 | 무리한 치환 없이 병기·도움말·예외로 처리되는가 |

표본은 실제 민원 원문을 무단 수집해 만들지 않는다. 공개 화면, 기관이 허용한 비식별 테스트 문구, 합성 예문만 사용한다.

### 7.3 제안하는 점수판

| 지표 | 계산 또는 확인 | 파일럿에서 보는 해석 |
|---|---|---|
| 정탐률 | 실제 수정 필요로 판정된 경고 ÷ 검토한 경고 | 낮으면 경고가 무시된다. |
| 오탐률 | 수정 불필요 또는 허용 예외 경고 ÷ 검토한 경고 | 법정·고유 용어에서 특히 낮아야 한다. |
| 제안 수용률 | 사람이 채택한 제안 ÷ 검토한 제안 | 문구 품질과 화면 맥락의 적합성을 본다. |
| 심각도 적합성 | 사람의 위험도 판단과 도구 등급의 일치 | 오류·경고·정보 분류를 조정한다. |
| 검토 시간 | 같은 문구 묶음을 수작업/도구 보조로 점검한 시간 | 속도만큼 검토 품질도 함께 본다. |
| 과업 결과 | 전후 완료율, 이해도, 혼동·문의 | 사용자 가치의 최종 증거다. |
| 운영성 | Rule Pack 변경 요청, 승인, 재검토 리드타임 | 기관이 실제로 유지할 수 있는지 본다. |

초기 목표 수치는 계약 약속이 아니라 파일럿 착수 때 합의할 가설이다. 다만 다음은 출시 불변 조건으로 둔다.

- 승인된 법정·기관 용어를 자동 변경하지 않는다.
- 모든 자동 제안은 사람이 적용·거절할 수 있다.
- 오프라인 설치판의 외부 통신·포트·자동 원문 저장은 0이어야 한다.
- 각 Rule Pack에는 근거, 승인자, 버전, 재검토일이 있어야 한다.

| 현재 위험한 유형 | 왜 중지해야 하는가 | 수정 원칙 |
|---|---|---|
| KRDS 고시·공식 준수 표현 | 공식 관계와 인증 범위를 과장할 수 있다. | 공식 자료를 참고한 독립 보조 도구, 최종 판단은 기관 검수라는 문구로 고친다. |
| KWCAG 100%, 전항목 Pass | 문구 도구만으로 접근성 전체를 판정할 수 없다. | 점검 항목·한계·별도 접근성 검수 책임을 명시한다. |
| 나라장터 규격 준수 | 조달 시스템 등록·규격·계약 적합성은 별도 사실 확인이 필요하다. | 발주별 조달·계약 담당자 확인 대상임을 적는다. |
| 특정 품목 코드·수의계약 기준 | 계약 금액, 발주기관, 시점, 계약 유형마다 달라진다. | 코드·방식은 삭제하고 개별 조달 검토 항목으로 바꾼다. |
| 고정 가격·지급 조건·무제한 SLA | 범위와 책임을 확인하지 않은 약속이다. | 발견 단계 뒤 견적·계약 협의라는 원칙으로 바꾼다. |
| 인증·보안 보장 | 설치판이 아직 없고 기관별 보안 승인이 다르다. | 검증 예정 항목, 책임 주체, 전제 조건을 명시한다. |

## 10. 최종 Go/No-Go 체크리스트

### 기관판 Release Go 조건

- [ ] 담당자 PC의 Windows 버전, 설치 권한, GitHub 직접 다운로드 또는 내부 반입 경로가 확인됐다.
- [ ] 기관판이 웹 데모·AI·서버·연구·제안서와 물리적으로 분리됐다.
- [ ] 앱의 네트워크 요청, 리스닝 포트, 자동 원문 저장, URL 원문 공유가 없음을 테스트로 증명했다.
- [ ] Rule Pack import는 스키마·크기·근거·버전·승인자·재검토일을 검증한다.
- [ ] 설치 파일과 tag, 버전 화면, SHA-256, SBOM, 코드 서명, 릴리스 노트가 일치한다.
- [ ] LICENSE, NOTICE, SECURITY, KRDS·제3자 출처 고지가 승인됐다.
- [ ] 개발·빌드·런타임 의존성 취약점의 판정과 예외 기록이 있다.
- [ ] 담당자 한 명이 문서만으로 설치·검사·저장·종료·업데이트 판단·롤백을 수행했다.
- [ ] 도구가 KRDS·접근성·법정 문구의 최종 판정을 대체하지 않는다는 고지가 앱과 Release에 있다.

### 파일럿 사업 Go 조건

- [ ] 핵심 여정 하나, 공개·비식별 표본, 담당자, 법정 문구 승인자, 보안 창구가 지정됐다.
- [ ] 도입 전 기준선과 성공 지표가 합의됐다.
- [ ] 업무·UX·접근성·보안 담당의 검토 경계가 문서로 정리됐다.
- [ ] Rule Pack의 유지·갱신 담당자가 지정됐다.
- [ ] 대외 제안 문구가 조달·인증·가격을 과장하지 않는다.

하나라도 충족되지 않으면, 기관용 설치판 Release는 중단한다. 대신 공개 문구만 사용하는 진단·교육·Rule Pack 설계 서비스로 범위를 낮추거나, 필요한 승인이 갖춰질 때까지 보류한다.
